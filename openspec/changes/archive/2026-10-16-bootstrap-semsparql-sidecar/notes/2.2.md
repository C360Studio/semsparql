# Task 2.2 developer notes — plain-BGP `SELECT` and `ASK` planner and executor

## Implementation choices

1. **Constrained-access BGP planner and dynamic bound-subject join upgrade (`sparql/planner.go`, `sparql/executor.go`):**
   - `planBGPWithScope` orders `BGPPattern` triple patterns by constrained-access selectivity (`accessEmpty` →
     `accessExactEntity` → `accessTypePattern` → `accessPredicate` → `accessFullScan`), preferring patterns whose
     subject variable or blank node has already been bound by an earlier step in the plan, and rejects BGPs with no
     selective anchor via `ErrUnconstrainedScan`.
   - During `evalBGP` execution, `pickBestRemainingStep` re-evaluates remaining steps against the live bound
     `Solution` set so that once an earlier pattern binds a subject variable `?target` to canonical entity IRIs, a
     subsequent pattern `?target <pred> ?val` is upgraded from a predicate or full-graph scan to exact entity hydration
     (`GetEntity` when 1 distinct entity ID is bound, or `GetBatch` when `> 1` distinct entity IDs are bound).
   - `lookupPredicateCandidates(predicateIRI)` expands standard predicate IRIs via `vocabulary.LookupByIRI(iri)`. An
     ordinary predicate IRI with no registered match in `vocabulary.LookupByIRI` is classified as `accessEmpty`,
     producing zero solutions and zero reader scans rather than a lookup error (`TestUnknownOrdinaryPredicateYieldsNoMatches`).

2. **Exporter-owned predicate and object RDF term conversion (`irimap.CanonicalNTriplesPredicateAndObject`):**
   - Stored `message.Triple` records on an `EntityState` are converted into virtual RDF triples by serializing a single
     probe triple `{Subject: "_:s", Predicate: tr.Predicate, Object: tr.Object, Datatype: tr.Datatype}` through
     `irimap.CanonicalNTriplesPredicateAndObject` (`export.SerializeToString(..., export.NTriples, export.WithBaseIRI(baseIRI))`).
   - Because `export` emits `_:s <predicateIRI> <canonicalNTriplesObject> .\n`, the executor obtains both the
     exporter-resolved predicate IRI and the exporter-classified RDF object term without duplicating `vocabulary/export`
     datatype or resource classification logic.
   - Virtual RDF triples per entity are deduplicated as a mathematical set before BGP matching, while solution
     sequences across joins and `UNION` branches preserve multiplicity unless `DISTINCT` is requested.

3. **Three-valued `FILTER` evaluation, deterministic `ORDER BY`, and query budgets:**
   - `evalFilterEBV` implements SPARQL 1.1 §17 three-valued logic for `!`, `&&`, and `||` (`false && error -> false`,
     `true || error -> true`, `!error -> error`, with top-level `FILTER` rejecting `false` and `error`).
   - Solutions are ordered before projection, `DISTINCT`, and `OFFSET`/`LIMIT` using explicit `OrderBy` conditions
     followed by a deterministic tie-breaker over all bound variables under the SPARQL 1.1 §15.1 total order
     (`Unbound < BlankNode < IRI < Literal`).
   - `Executor` enforces `DefaultQueryTimeout` (`10s`), `DefaultMaxResults` (`10,000`, bounding both output bindings and
     intermediate solution buffers), and `DefaultMaxScanEntities` (`100,000`), returning classified
     `ErrResultLimitExceeded` (`sparql_result_limit_exceeded`), `ErrScanBudgetExceeded` (`sparql_scan_budget_exceeded`),
     or `ErrQueryTimeout` (`sparql_query_timeout`). Explicit truncation consent (`Config.AllowTruncation` or
     `WithAllowTruncation(true)`) returns the partial result with `Truncated: true` and
     `TruncationReason: "result_limit" | "scan_budget"` for result/scan caps while keeping timeouts fail-closed.
